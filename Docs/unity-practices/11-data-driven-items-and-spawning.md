# 11 - Data-driven items, runtime spawning, pooling, and save-friendly state

Researched 2026-10-18 from Unity manual / script reference pages (6000.0, 6000.3, 6000.6), a Unity Learn page, and a handful of community write-ups (flagged where used). No Unity commands were run; no project files were edited.

## 1. Question

Should item definitions be ScriptableObjects or JSON/CSV? How do we instantiate hundreds of items at room load, when does pooling (`UnityEngine.Pool.ObjectPool`) pay off, what are the GC/allocation concerns, how do we design state so it can be saved (IDs, not references), and what are the common ScriptableObject-at-runtime pitfalls? Plus a minimal architecture for "items are data, instances are spawned on demand, state is stored when a room unloads".

## 2. Findings

### ScriptableObject vs JSON/CSV for definitions

- ScriptableObject (SO): a `UnityEngine.Object` asset used "as a container for shared data used by multiple objects at runtime, which can reduce a project's memory usage by avoiding copies of values" - one copy in memory instead of one per prefab instance. Source: https://docs.unity.com/en-us/engine/6000.3/manual/scripting/get-started/fundamental-unity-types/class-scriptable-object.md
- SOs can reference other assets (prefab, material, mesh, sprite) directly in the Inspector; Unity serializes a reference to a `UnityEngine.Object`, not a copy: "When you reference a class derived from UnityEngine.Object ... Unity only serializes the reference ... the data is only serialized once." Source: https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/code-reload-serialization/script-serialization/best-practices.md . JSON cannot hold such references; it would need a key/path that you resolve yourself (UNSOURCED GUESS on exact resolution strategy).
- In a built Player you can only **read** SO assets: "In a standalone Player at runtime, you can only read saved data from the ScriptableObject assets." In the Editor, "Unity automatically writes the data to disk and it persists between Editor sessions" when you modify via the Inspector; script edits to SOs in Edit mode need `EditorUtility.SetDirty` or "changes may not persist". Source: SO manual page above. (The page does not explicitly say what happens to script-made runtime changes to an SO in Play mode in the Editor; see forum evidence below.)
- JsonUtility: fields only, no `Dictionary<>`, no top-level primitives/arrays (wrap them in a class), `[Serializable]` required; it ignores unknown JSON keys and leaves missing fields at constructed defaults. Deserialising into a MonoBehaviour/ScriptableObject must use `FromJsonOverwrite` (`FromJson` throws). Allocation: `ToJson` allocates GC only for the returned string; `FromJson` only for the returned object and sub-objects; `FromJsonOverwrite` allocates nothing if overwritten fields are value types; usable from a background thread. Unity states benchmarks show it is "significantly faster than popular .NET JSON solutions" though with fewer features. Source: https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/code-reload-serialization/script-serialization/json-serialization.md
- Unity serialization rules: no support for multidimensional/jagged arrays, dictionaries or nested containers (wrap in a class/struct or use `ISerializationCallbackReceiver`); custom classes serialize inline by value by default, cannot be null (replaced by an object with default fields) unless `[SerializeReference]`; `[SerializeReference]` costs some overhead. Source: https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/code-reload-serialization/script-serialization/rules.md
- Unity serialization best practice: serialize the smallest set of data; never serialize duplicate/cached data; keep SO class structure "flat and simple"; large nested custom-class structures become hard to migrate. Source: .../script-serialization/best-practices.md (URL above).
- CSV: I found no Unity source covering CSV specifically. UNSOURCED GUESS: CSV is a reasonable authoring format (spreadsheet) for tabular data like 340 book titles/categories but needs an Editor-time importer that generates SO assets (or a runtime parser); at runtime you would still want typed C# objects.
- Newtonsoft/Json.NET as a general-purpose companion: Unity's JSON page says "you can use a general purpose .NET JSON library as a companion to the JsonUtility API" for things its serializer does not support (same JSON page). It does not name the package; UNSOURCED GUESS that the `com.unity.nuget.newtonsoft-json` package is the official route (not checked here).
- Resources folder: Unity advises avoiding "a lot of content" in `Resources` - slows startup/build, "uses memory proportional to the number of objects, even if they aren't loaded", always included in builds. For large/updatable content it recommends AssetBundles or Addressables. Source: https://docs.unity3d.com/6000.0/Documentation/Manual/LoadingResourcesatRuntime.html . Implication: do not use `Resources.LoadAll` as the item-database mechanism; reference definitions from a serialized list in a registry SO instead (the registry and its entries are then loaded with whatever references it). The registry idea itself is a design synthesis, UNSOURCED beyond the Resources guidance.

### ScriptableObject-at-runtime pitfalls

- With domain reload disabled, non-serialized fields in already-loaded SOs persist between Play sessions: "Non-serialized fields keep the values assigned to them during Play mode on returning to Edit mode ... ScriptableObjects" (https://docs.unity.com/en-us/engine/6000.6/manual/programming-environment/code-reload-serialization/code-reload/code-reloading-editor/domain-reloading.md). See file 13.
- Forum/blog evidence (not official docs; lower confidence): in the Editor, writing a runtime value into an SO *asset* modifies the project asset and is not reverted on exit; in a build the change is in-memory and lost on quit; if many MonoBehaviours reference the same SO asset, one's mutation is seen by all; the commonly recommended fix is to treat SO assets as read-only configuration, `Instantiate`/`CreateInstance` a copy for per-instance runtime state, or keep runtime state in a plain C# object. Sources: https://discussions.unity.com/t/prevent-custom-scriptableobject-asset-persisting-changes-after-exiting-play-mode/545928 , https://discussions.unity.com/t/scriptableobject-data-is-persistent-between-game-restarts-but-not-between-unity-editor-restarts/1552442 , https://bugnet.io/blog/how-to-fix-unity-scriptableobject-values-persisting
- `OnValidate` on an SO is Editor-only (runs when the script loads or a value changes in the Inspector) - good for validating unique IDs at authoring time, but it does not run in builds. Source: ScriptableObject reference: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ScriptableObject.html
- Class name must match the file name (BookBoy CLAUDE.md already notes this; the Unity manual note says "The script file must have the same name as the class.", SO manual page).

### Instantiation and pooling

- `Instantiate` clones the GameObject and all child objects/components; `Awake`/`OnEnable` run "only if it's active in the hierarchy when you call this method"; the clone keeps the original's active state (so instantiating from an inactive prefab template gives an inactive clone - useful to configure before activation); no prefab connection is created. Source: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Object.Instantiate.html . The page gives no performance guidance.
- `Object.InstantiateAsync` exists in Unity 6: overloads for a single copy and for `count` copies, with `positions`/`rotations` spans (spans repeat modulo length if shorter than count), `InstantiateParameters` (parent, scene, world/local space), cancellation tokens; mostly asynchronous but "the final stage, which covers integration and Awake calls, runs on the main thread"; `WaitForCompletion()` forces sync. Source: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Object.InstantiateAsync.html . Unity issue UUM-102307 reports main-thread spikes with InstantiateAsync of a single very large prefab (fixed in 6.0-6.3 patch lines per a search summary; check the exact patch): https://issuetracker.unity.com/issues/20485/long-scheduler-times-on-main-thread-when-using-instantiateasync-with-a-singular-massive-prefab
- I found **no authoritative per-Instantiate millisecond number** for Unity 6; community advice is that cost scales with prefab complexity (children, component count, skinned meshes) more than raw count, and to measure. Forum evidence only: https://discussions.unity.com/t/instantiate-is-taking-up-to-300ms-after-creating-a-large-number-of-objects-in-edit-mode/247225
- Pooling guidance from Unity Learn (design-patterns course): "profile your code every time you instantiate a large number of objects"; pool "if you detect significant spikes that put your gameplay at risk of stuttering"; pre-instantiate "during a loading screen"; reused objects are "dirty items" that must be reset (e.g. Rigidbody velocity); deactivating pooled objects stops their Update; pooling adds complexity and can waste memory "if you create pools prematurely". Source: https://learn.unity.com/course/design-patterns-unity-6/tutorial/use-object-pooling-to-boost-performance-of-c-scripts-in-unity
- `UnityEngine.Pool.ObjectPool<T>` constructor takes createFunc, actionOnGet, actionOnRelease, actionOnDestroy, collectionCheck, defaultCapacity, maxSize; `Get` creates a new instance if the pool is empty; releasing into a full pool destroys the instance via actionOnDestroy; `collectionCheck` throws on double release (Editor only per the Learn page); not thread-safe; has `CountActive/CountInactive/CountAll`; `Clear`/`Dispose` destroy all pooled items. Source: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Pool.ObjectPool_1.html
- `ListPool/HashSetPool/DictionaryPool` (`CollectionPool`) give pooled temporary collections; `Get(out list)` inside `using` returns it automatically. Source: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Pool.CollectionPool_2.html
- GC: Unity runs the collector when an allocation cannot fit; during heavy load operations temporary objects Unity still references prevent release and the heap expands; "ideally to 0 bytes per frame". Example from the manual: 1 KB per frame at 60 fps is 3.6 MB per minute. Source: https://docs.unity.com/en-us/engine/6000.3/manual/analysis/performance-memory/managed-memory/garbage-collector.md . Unity's pooling page for managed memory: https://docs.unity.com/en-us/engine/6000.3/manual/analysis/performance-memory/managed-memory/optimizing-code-managed-memory.md
- Physics detail relevant to prefab design: a collider with no Rigidbody is a *static collider*; kinematic colliders are not driven by forces but can wake others; moving a static collider by Transform is "generally discouraged" because physics "cannot immediately take Transform-led movement into consideration". Source: https://docs.unity3d.com/6000.0/Documentation/Manual/collider-types-introduction.html . So a shelved book = collider only (no Rigidbody) is the cheapest correct state; add a Rigidbody when it is picked up/thrown and remove or make kinematic when it settles on a shelf. UNSOURCED GUESS: toggling `isKinematic` vs adding/removing the component; Unity's page does not compare their costs.

### Save/load-friendly state: IDs not references

- `Object.GetInstanceID()` "is not reliable for performing actions that could span between sessions, for example, loading an object state from a file"; it changes between sessions. In 6000.6 the method is marked **Removed** in favour of `GetEntityId`. Source: https://docs.unity.com/en-us/engine/6000.6/script-reference/unityengine/object/getinstanceid.md (the same non-persistence caveat applies to EntityId by the same reasoning - UNSOURCED GUESS).
- Community guidance: save files should store IDs or simple values rather than references to scene objects, use `Application.persistentDataPath`, include a version number, write to a temp file and rename for atomicity. Sources (community): https://gamineai.com/blog/game-save-systems-implementing-persistent-data-unity , https://bugnet.io/blog/game-save-best-practices-unity , https://gamedev.net/blogs/entry/2266731-building-a-save-system-for-level-objects-in-unity-pt-2-usable-objects (the last one could not be fetched; its description comes from a search summary).
- Unity serialization rules also say references to `UnityEngine.Object` are serialized as asset references, which only works for assets in the project, not for runtime-created instances (follows from the rules page). Persisted state therefore needs a stable ID you control. (UNSOURCED GUESS on how to generate: a string id typed or generated at authoring time, validated unique in `OnValidate`.)

## 3. Numbers and rules of thumb

- GC: target 0 bytes/frame in gameplay; 1 KB/frame at 60 fps = 3.6 MB/min (Unity GC manual).
- ObjectPool example in Unity's Learn sample: defaultCapacity 20, maxSize 100 (just an example, not guidance).
- No Unity-published cost per Instantiate call. UNSOURCED GUESS (order of magnitude, from experience): hundreds of simple one-mesh prefabs instantiate in a handful of milliseconds up to tens of ms on a PC; measure with Profiler. Do not treat as fact.
- JsonUtility vs other JSON libs: "significantly faster" per Unity (no numbers).

## 4. Confidence

- High: SO read-only in Player, JsonUtility rules, ObjectPool API semantics, GetInstanceID non-persistence, Resources folder advice.
- Medium: pooling advice (Unity gives qualitative guidance only), InstantiateAsync behaviour.
- Low: any statement about Instantiate speed at this project's scale; ScriptableObject runtime-mutation behaviour comes mostly from forum/blog sources plus the official domain-reload page.
- Unknown: how Rigidbody add/remove vs kinematic toggle compare in cost; whether `Object.InstantiateAsync(count)` is worth it for ~110 items per room (likely not needed unless a measured load hitch appears).

## 5. Implication for BookBoy

Recommended **minimal architecture** (a synthesis of the sources above; the specific shape is design advice, not a quote from Unity):

1. **Definition layer (read-only data):** keep `BookDefinition` ScriptableObjects. Add (or confirm) a stable `string Id` on each, unique, validated in `OnValidate`. Fields: id, display name, category, material, size/spine data, etc. Do not store anything in the SO that changes during play (counts, shelf position, found/not found). One definition can be shared by many instances.
2. **Registry:** one `ItemCatalog` SO holding a serialized list of all definitions, referenced from the scene (not `Resources.LoadAll`). Build an `Id -> definition` dictionary on startup (not serialized; reset it per section 13 rules if static).
3. **Runtime state layer (plain C#, no Unity references):** `ItemState { string Id; string DefId; Vector3/Quaternion pos/rot or SlotId; State enum (OnShelf, InPile, Held, Thrown...) }`. A `RoomState` owns a `List<ItemState>` plus room flags (door open, etc.). This is the thing that is saved/loaded and kept when a room unloads. Use simple value types and string IDs so JsonUtility can write it (wrap lists in a class; no dictionaries).
4. **View layer:** one item prefab (cube mesh, collider, `Book` component) – a single template, instantiated per `ItemState` on room load, configured from the definition (material via `sharedMaterial`, size via scale), parented to the room root. `Book` holds only the `ItemState` it represents (or its Id), not the definition data copy.
5. **Room unload:** for each item view, write transform/slot back into its `ItemState`, then destroy (or release to a pool) the views. **Room load:** for each `ItemState`, get a view from a pool and apply state. Rooms 2 and 3 never loaded stay as state only until opened.
6. **Pooling:** start with plain `Instantiate`/`Destroy` per room load (about 110 items per room, one simple prefab). Add an `ObjectPool<Book>` only if the Profiler shows a load hitch or GC spike, or for thrown/transient objects that are created repeatedly. When pooling: reset Rigidbody state, outline state, parent, active flag, in `actionOnRelease`/`Get`. Unity itself says profile first and avoid premature pools.
7. **Physics state:** shelved items = Collider (trigger) only, no Rigidbody, per Unity's static-collider model. Add a Rigidbody (or enable non-kinematic) only for pickup/throw; after settling, write position into state and remove/kinematic it. For baked piles, store the baked positions in `ItemState` and keep them as plain static-collider objects; to avoid "kick" physics add no Rigidbody until the player actually interacts.
8. **Do not** write runtime values into SO assets; with skip-domain-reload ON they will leak between Play sessions and in the Editor they can overwrite authored assets (file 13).

Where current choices look right or wrong given the brief:
- Right: ScriptableObject `BookDefinition` per item, one material per colour group, items as prefab-like cubes. This matches Unity's guidance for authoring-time data with asset references.
- Risky: creating the BookOutline helper's hull renderers, light and particle system at runtime on highlight - fine if only one item is highlighted at a time, but each creation allocates; consider a single shared outline rig that follows the highlighted item (pool of one). This is a design suggestion, not sourced.
- Risky: per-item `Renderer.material` access (clones materials; see file 10). Use `sharedMaterial`.
- JSON for definitions is not needed now; consider JSON only for the **save file** (state layer), via `JsonUtility` with `[Serializable]` classes, in `Application.persistentDataPath`, with a `version` field. CLAUDE.md says present a plan before building save/load (F-003), so treat the state layer as the plan input rather than starting implementation.
- Smallest first step: introduce `string Id` on definitions and an `ItemState` class and have the existing placement/baked-pile code write/read it, before touching room loading.
