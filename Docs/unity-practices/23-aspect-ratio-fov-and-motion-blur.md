## 1. Question

(a) How does Unity handle aspect and resolution on a game that targets 16:9 only, including windowed odd sizes? (b) How do shipped games and Steam players expect FOV (axis, slider range, default), how do we present a horizontal slider in a vertical-FOV engine, and what does FOV change about the apparent size of near objects and edge distortion? (c) What does URP Motion Blur actually do, why do accessibility guides want it off or toggleable, what does motion sickness research say, and does blur hurt reading spine text while turning? (d) What settings menu and defaults should a Steam release have?

## 2. Findings

### 2.1 Aspect ratio and resolution in Unity (what matters for 16:9)

- `Camera.aspect` is computed automatically from the screen aspect, "even when the camera doesn't render to the full screen area"; setting it manually overrides it until `ResetAspect()`. [fetched, summarised by fetch model] https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Camera-aspect.html
- Unity's FOV is vertical; the horizontal view follows the aspect ratio (Hor+). So every window shape from 4:3 to 32:9 renders without bars or stretching, and only the horizontal angle changes. [fetched] https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Camera-fieldOfView.html and Wikipedia calls Hor+ "the most common method today" https://en.wikipedia.org/wiki/Field_of_view_in_video_games . Cinemachine 3 `LensSettings.FieldOfView` is also vertical. [fetched] https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/api/Unity.Cinemachine.LensSettings.html . The Brain page covers lens mode override (Perspective/Physical) and update timing but says nothing about aspect or FOV axis [fetched] https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/CinemachineBrain.html ; I found no Cinemachine page that describes aspect-change behaviour, so "it just stays vertical" is inferred from the two facts above.
- Fullscreen modes (Windows): **Fullscreen Window** = borderless at native desktop resolution; "Unity renders the app content at the resolution set by a script, or the native display resolution if none is set and scales it to fill the window. When scaling, Unity adds black bars ... called letterboxing." **Exclusive Fullscreen** (Windows only) "changes the OS resolution of the display". **Windowed** is resizable by default unless **Resizable Window** is off. **Maximized Window** is a full-screen window with a title bar. [fetched] https://docs.unity.com/en-us/engine/6000.6/manual/platform-specific/windows/playersettings and https://docs.unity3d.com/6000.0/Documentation/ScriptReference/FullScreenMode.html
- Other Player Settings: Run In Background (when off the app pauses on focus loss), Visible in Background (windowed only; blocks Alt+Tab minimise shortcuts), Allow Fullscreen Switch (OS key presses toggle full/windowed). The 6000.6 page has no "Supported Aspect Ratios" or resolution-dialog entry; I found no Unity setting that enforces 16:9 in 6000.6. [fetched, absence]
- `Screen.SetResolution(w, h, FullScreenMode[, RefreshRate])`: "If no exact match is supported, the closest one is set"; exclusive fullscreen and refresh-rate changes are Windows-standalone only; takes effect "at the end of the current frame"; in multi-display setups only the primary screen is settable. [fetched] https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Screen.SetResolution.html
- `Screen.resolutions` lists "all full-screen resolutions that the monitor supports" for the current monitor, each with a refresh rate (so the same width x height can appear several times). For exclusive fullscreen use it to choose; unsupported sizes there "can severely impact performance", while other modes accept arbitrary sizes. [fetched, summarised] https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Screen-resolutions.html
- Calling `SetResolution` with an aspect that differs from the desktop in Fullscreen Window gives black bars by design; a Unity issue entry marked this "by design" and noted the chosen size was lost when toggling modes because Unity fell back to a PlayerPrefs default. [search-only] https://issuetracker-mig.prd.it.unity3d.com/issues/extra-space-appears-below-and-above-application-when-using-screen-dot-fullscreen-to-expand-and-contract-the-window
- No built-in way to lock a resizable window to 16:9 was found; the usual answer is a Windows plugin handling `WM_SIZING` (my inference, not confirmed by any page). [search-only, absence] https://adventurecreator.org/forum/discussion/comment/60558/ . Community letterboxing via `Camera.rect` exists (full-width reduced-height rect, plus a second black-clear camera behind it for the bars); pitfalls reported include particles and other content drawing in the bars. [search-only] https://discussions.unity.com/t/how-do-i-set-the-aspect-ratio-of-the-viewport/9353 . `Camera.rect` is normalised viewport coordinates (0,0 bottom-left); the page offers no aspect helper. [fetched] https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Camera-rect.html
- UI: Canvas Scaler "Scale With Screen Size" takes a Reference Resolution and a Screen Match Mode (Match Width Or Height with a 0-1 slider, Expand, Shrink); this is the hook that decides how UI follows a non-reference aspect. [fetched] https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/script-CanvasScaler.html . Recommending Match = 1 (height) for a Hor+ game is my reasoning (UI then keeps its size relative to the vertical view that the camera fixes): UNSOURCED GUESS.
- Who plays at what size: Steam survey reports conflict. Mid-2025 report: 1080p 54.54%, 1440p 19.86%, 4K 4.49%; a March 2026 report: 1080p 45.04%, 1440p 38.64%, 4K 3.06% (one-month jump of 17 points looks suspect, unverified against Valve). Ultrawide below 1% each in an older write-up. [search-only] https://automaton-media.com/articles/newsjp/steam-20260303-425951/ and https://www.pcgamesn.com/steam-hardware-survey-resolution . Steam Deck is 1280x800 (16:10) preferred, 1280x720 alternative; Valve requires UI text of at least 9 px high at 1280x800 (12 px recommended). [fetched] https://partner.steamgames.com/doc/steamdeck/compat . That is a UI rule; diegetic spine text is not covered.

### 2.2 Horizontal vs vertical FOV: convention and slider ranges

- Convention is mixed. Historically game FOV meant horizontal (Quake era; Unreal treats it as horizontal) per a Gearbox developer post [search-only; page 403] https://www.gearboxsoftware.com/?p=10284 . Engines like Source only know the vertical angle and compute horizontal from aspect; a TF2 forum argued its slider is really vertical [search-only] https://www.wsgf.org/phpBB3/viewtopic.php?p=55622 .
- Concrete shipped conventions: Counter-Strike 2 and Apex Legends: horizontal with a Source-style 4:3 base (90 -> 106.26 horizontal at 16:9; Apex slider 70-110); Valorant: fixed 103 horizontal at 16:9 base; Battlefield 2042: vertical, 50-105. [fetched] https://dev.to/keyboard-testerclick/why-the-same-fov-feels-different-across-games-hfov-vs-vfov-2blf . Because bases differ, the same number is not the same view across games.
- Ranges and defaults: PC sliders in the 60-120 band (Black Ops Cold War 60-120; Vanguard 60-120, default 80; Battlefield 6 85-120). [search-only] https://www.thegamer.com/black-ops-cold-war-fov-all-platforms/ and https://www.magicgameworld.com/battlefield-6-how-to-adjust-fov/ . PCGamingWiki glossary (quoted second-hand): design PC games with roughly 85-110, console 55-75 [search-only]. Wikipedia: console about 60, PC 90-100, axis often unstated. [fetched] https://en.wikipedia.org/wiki/Field_of_view_in_video_games
- Relaxed / object-focused references: **Firewatch** default 55 vertical (about 85 horizontal at 16:9), no slider, changeable by registry (value is 100x degrees added). [fetched help page, axis from search summary of WSGF] https://help.panic.com/firewatch/fov/ and https://www.wsgf.org/node/29393 . **PowerWash Simulator** FOV 60-100, default 70, axis not stated (community wiki, last edited April 2023). [fetched] https://powerwashsimulator.wiki.gg/wiki/Options . **House Flipper 2**: slider minimum 60; articles advise 70+; default unconfirmed. [search-only] https://dotesports.com/?p=1194033 . **Witch Cabin Cleanup**: 90 default with reset, axis unknown (repo note, doc 02).
- Accessibility sources: Xbox Accessibility Guideline 117 says provide "adjustable FOV so players can choose the angle that causes them the least discomfort, based on their seating distance", cites Halo Infinite's FOV slider with an explanation of the "fishbowl" effect at higher angles, and Minecraft up to 110. [fetched] https://devdocs.xbox.com/gaming/accessibility/xbox-accessibility-guidelines/117 . Game Accessibility Guidelines (Intermediate tier): if a 3D game uses FOV, let players adjust it; a good default helps but cannot fit every screen size and viewing distance; more important on PC than console. No numeric range given. [fetched] https://gameaccessibilityguidelines.com/if-the-game-uses-field-of-view-3d-engine-only-allow-a-means-for-it-to-be-adjusted/
- Players cannot tell an axis without a label, so label it. The dev.to comparison tells you to record the axis and reference ratio before comparing numbers. [fetched] dev.to link above.

### 2.3 Conversion maths, presenting a horizontal slider

- Unity has both converters: `Camera.HorizontalToVerticalFieldOfView(hFov, aspect)` (listed [fetched] https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Camera.HorizontalToVerticalFieldOfView.html) and `Camera.VerticalToHorizontalFieldOfView` (doc 02). Formula: V = 2 atan(tan(H/2) / A), H = 2 atan(tan(V/2) * A). Multiplying the angle by 16/9 is wrong. [fetched] dev.to link above.
- Design choice: define the slider as horizontal at a fixed 16:9 reference, convert to vertical with aspect 16/9 (not the window's aspect), and write that to `Lens.FieldOfView`. Then the vertical view is the same for every window shape (it is Hor+ for other shapes) and the number the player sees is stable. [derived design, built from the sourced facts above]

### 2.4 FOV, apparent size, closeness, distortion (additions to doc 02)

- Fixed distance: wider FOV = smaller on screen (doc 02 table). Wider FOV does not make things feel "closer"; if anything it pushes the player to step closer to keep the same size. Adding for letters: a 0.02 m spine letter at 1.5 m is [derived, assumed letter height is an UNSOURCED GUESS] 9.4 px tall at 1080p with 75 v, 12.5 px at 60 v, 12.8 px at 58.7 v (90 h), 15.4 px at 50 v; at 1440p 12.5 / 16.6 / 17 / 20.6 px; at 4K 18.8 / 24.9 / 25.5 / 30.9 px. At 2 m on 1080p with 75 v it is 7.0 px. Resolution helps as much as FOV, so 1080p is the worst case to design for.
- Edge stretch (doc 02): 1.69x tangential and 2.86x radial at 53.75 degrees off axis (the 16:9 side edge of 75 v). It scales with the angle, so 90 h (edge 45 degrees) has 1.41x / 2.0x. Xbox's guideline calls the same effect "fishbowl" at higher angles. [derived plus fetched Xbox page]
- Eye height: the camera position sets perspective, FOV sets framing (Wikipedia perspective-distortion and dolly-zoom pages in doc 02). Raising the eye to 1.6-1.7 m puts the camera above most shelf boards, so the player looks down on the lower boards at a steeper angle; that raises foreshortening of the spine plane, not the FOV. UNSOURCED GUESS on the felt effect; geometry is derived only.
- Viewmodel: Unity's Render Objects Field Of View override is vertical (doc 04), so if a viewmodel FOV is added later, derive it from the same slider (for example keep the ratio of tan(half-angle) fixed) or the held book will change size relative to the world as the slider moves. UNSOURCED GUESS on keeping the ratio; the vertical axis is sourced.

### 2.5 Motion sickness evidence (honest summary)

- The best desktop-style study found: TNO, 20 participants, a Source-engine tour on a rear-projection screen, internal (rendered) and external (viewing geometry) vertical FOV 30 or 60 degrees, 50 minutes each. Result: absolute FOV size had no clear significant effect on sickness ("absolute FOV size itself not necessarily affects sickness"); mismatched conditions were less sick than matched ones, opposite to the hypothesis; habituation across sessions was significant; 8 of 20 participants stopped at least one session. Authors note typical players view the screen at about 30 degrees vertical while engines use 75-90 vertical. [fetched, extracted from the paper PDF] https://www.ieda.ust.hk/dfaculty/so/pdf/Pages89-95-VIMS2007.pdf . Limits: 2007, projector, small N, forced erratic swaying, a very large FOV mismatch.
- The same paper cites a review saying both small and wide FOVs may induce nausea, and notes optic flow differs by FOV (low FOV gives large translational flow on turning; high FOV gives bigger divergent flow when moving). [fetched, same PDF]
- Wikipedia says a narrow FOV "may lead to disorientation, dizziness, or nausea" (consoles ported to PC "binoculars"); Gearbox reportedly warned that console FOV at desk distance caused tunnel vision/sickness; a 2025 VR paper says larger FOV raises sickness probability. These disagree about direction: narrow is bad (desktop commentary), wide is bad (VR), and TNO found no clear FOV effect. [fetched Wikipedia; search-only others] https://en.wikipedia.org/wiki/Field_of_view_in_video_games and https://www.scitepress.org/Papers/2025/136994/136994.pdf
- Mitigation research is VR: a 32-person study found no significant difference in sickness among FOV reduction, depth-of-field blur and a rest-frame reticle; FOV reduction and blur lost task information, the reticle did not. [fetched, from paper PDF] https://arxiv.org/pdf/2103.05200 . Subtle dynamic FOV restriction (soft cutout that grows with speed) significantly reduced VR sickness in Fernandes and Feiner (IEEE 3DUI 2016); most participants using the subtle version did not notice it. [search-only] https://www.sciencedaily.com/releases/2016/06/160614121922.htm . Neither is a desktop result. Static Vignette 0.2 in the project is not the same as speed-driven restriction.
- Guides: Game Accessibility Guidelines list asynchronous weapon/walk bob, motion blur, chromatic aberration, mouse smoothing and camera shake/tilt as mismatches; "if a game uses them, provide an option for people to turn them off"; more mismatches = more risk (Intermediate tier). [fetched] https://gameaccessibilityguidelines.com/avoid-or-provide-option-to-disable-any-difference-between-controller-movement-and-camera-movement/ . Xbox 117: let players "disable or reduce camera shake, camera bobbing, motion blur, and mouse blur", avoid repetitive side-to-side or up-and-down movement outside core gameplay, separate horizontal and vertical sensitivity, and let players disable automatic camera movement; intensity sliders 0-100% as in Halo Infinite; ESO has head-bob intensity. [fetched, link above]
- Anecdote, not research: a player writer calls head bob their most common trigger and says motion sickness affects "up to one third of people" (no citation). [fetched, author opinion] https://madelinemiller.dev/blog/motion-sickness-accessibility/ . A search of consumer guides found no peer-reviewed non-VR study isolating head bob, FOV or motion blur with symptom scores. [search-only, absence]

### 2.6 What URP Motion Blur does

- Unity 6000.6 manual: effect "simulates the blur ... when a real-world camera films objects moving faster than the camera's exposure time"; "URP only blurs camera motions"; **Mode**: Camera Only (no motion vectors, better performance) or Camera and Objects ("GameObject motion vectors overwrite the camera motion vectors"); **Quality** presets; **Intensity** 0-1; **Clamp** 0-0.2, default 0.05, "maximum length that the velocity resulting from Camera rotation can have ... as a fraction of the screen's full resolution". The page contradicts itself ("only blurs camera motions" vs a Camera and Objects mode); I would trust the Mode table. [fetched] https://docs.unity.com/en-us/engine/6000.6/manual/post-processing-and-full-screen-effects/urp/effect-list/motion-blur.md
- Shader (Unity Graphics master `CameraMotionBlur.shader`, read through a summarising fetch, so quoted lines are limited): Camera Only reconstructs each pixel's world position from the depth buffer, projects it with the previous and current view-projection matrices and takes the difference as velocity; `velocity = GetCameraVelocity(...) * _Intensity`; the vector is clamped to `_Clamp` keeping its direction; zero velocity gives zero blur; Low/Medium/High = 2/3/4 iterations, each taking one forward and one backward sample along the velocity (4/6/8 taps total) with jittered offsets. [fetched] https://raw.githubusercontent.com/Unity-Technologies/Graphics/master/Packages/com.unity.render-pipelines.universal/Shaders/PostProcessing/CameraMotionBlur.shader . The scale of the "projected position" (a 0.5 factor lives in the vertex shader) was not shown, so absolute blur length in pixels is an inference.
- Consequences [derived from the shader description]: (1) blur exists only while the camera moves; a still view is perfectly sharp. (2) Velocity is the previous-frame difference, so blur length scales with per-frame motion and shrinks as frame rate rises. (3) Camera rotation moves every pixel (depth only matters for translation), so a mouse flick smears the whole frame, shelf and books included.
- Rough size: at 1080p, 75 v, a 180 deg/s turn moves the screen centre 36.9 px per frame at 60 fps (15.4 px at 144 fps); at 360 deg/s, 74 px (30.7 at 144). With Intensity 0.6 and samples spread both ways, a spine at screen centre smears over a few tens of pixels at 60 fps if the velocity is in UV units as the shader suggests [derived; the 0.6 times / plus-or-minus spread is an inference]. The default clamp (5% = 96 px at 1920 wide) is not reached by these speeds, so Clamp does not protect readability here. A spine letter stroke is 1-2 px, so any of this erases letterforms during the turn.
- Readability reports: an Atlas Fallen thread says text could not be read while turning at high fps until both motion blur and radial blur sliders were zeroed; Unreal's UDK docs list the same mitigations (less blur, mask to screen edges, limit for critical gameplay, higher frame rate). [search-only] https://steamcommunity.com/app/1230530/discussions/0/6363076374189910987 and https://docs.unrealengine.com/udk/Three/MotionBlur.html (page 403 to me). I found no source saying blur is unnecessary at 60 fps or a controlled readability test.
- Who dislikes camera blur: forum commentary separates camera blur (disliked) from object blur (liked) and says games often tie both to one option. [search-only] https://www.guru3d.com/publish/comments/preview-amd-fidelityfx-super-resolution/page-11 . Dot Esports advises turning motion blur off in House Flipper 2 to reduce discomfort. [search-only] https://dotesports.com/?p=1194033 . Anecdote-level.
- Does the user's turning speed make the player want to read spines while turning? Not tested. The relevant moment is the glance after the turn settles; with blur this is sharp again within one frame because blur is velocity-based. The cost is during the turn only, plus the habit of scanning shelves by sweeping the mouse. UNSOURCED GUESS on the scan habit.

## 3. Numbers and rules of thumb

- Hor+ in Unity: set vertical FOV once; the horizontal angle moves with the window.
- Slider semantic: "horizontal at 16:9" = `Camera.HorizontalToVerticalFieldOfView(h, 16f/9f)`. 70-110 h = 43.0-77.6 v. Default candidates: 90 h (58.7 v, about Firewatch/Source-feel), or 100 h (67.7 v), or the current 107.5 h (75 v).
- 16:10 at 75 v = 101.7 h; 4:3 = 91.3; 21:9 (64:27) = 122.4; 32:9 = 139.7.
- Letter legibility at 1080p, 1.5 m, 0.02 m letters: 9.4 px at 75 v, 12.8 px at 58.7 v (derived).
- Motion blur: Intensity 0.6, Clamp 0.05; blur ~ per-frame camera displacement; 180 deg/s at 60 fps = about 37 px of screen motion per frame at 1080p and 75 v (derived).
- Settings from references: FOV 60-100 default 70 (PowerWash), 85-120 (Battlefield 6), 60-120 default 80 (Vanguard), 55 fixed vertical (Firewatch), sliders 0-100% for motion effects (Halo Infinite, XAG 117).

## 4. Confidence and unknowns

- **High**: Unity's FOV is vertical and aspect-driven; fullscreen-mode behaviour and letterboxing (Unity manual); URP motion blur is velocity-based, camera-wide for rotation and zero when still; every conversion number.
- **Medium**: absolute blur size in pixels (inference from a summarised shader); that blur hurts spine reading (plausible, supported by one forum thread and Unreal's own mitigation list, no controlled test); Steam resolution shares (conflicting reports).
- **Low**: which FOV axis Witch Cabin, PowerWash and House Flipper 2 use; whether wide or narrow FOV is safer on a desktop (sources disagree; only one old small TNO study read first-hand); head-bob effects in non-VR games (anecdotes and guidelines, no study found); PCGamingWiki ranges (quoted second-hand).
- Not found: a Unity page on aspect-locking a window; a Cinemachine page on aspect changes; a GDC talk on FOV or blur choices for tidying or cozy games; a study of motion blur and text legibility during camera rotation.
- Open checks to do in the Editor later (not done here): measure real spine glyph height in px at 1080p; confirm Cinemachine keeps `Camera.rect` untouched if letterboxing is ever added; confirm the default Starter Assets look stays smooth with `FrameRateCap` at 144 Hz.

## 5. Implication for BookBoy

Keep the blast radius small. Nothing below was applied.

1. **Motion blur: switch it off by default (smallest change: Global Volume Motion Blur override off, or intensity 0).** Rationale: Game Accessibility Guidelines and Xbox 117 both treat blur as something to offer off, the effect only costs us while the camera moves, and the game's central act is reading small spine text during mouse sweeps. The owner can still get a "juicy" look from Bloom and Vignette. If kept at all, offer it as a toggle, Camera Only, Low quality, Intensity 0.2-0.3, and note it is a separate decision from the sickness question. Default OFF is my recommendation, not a sourced number.
2. **FOV: adopt a horizontal-at-16:9 slider, range 70-110, default 90 (58.7 v), step 1, with a reset button.** Reasons: players expect horizontal sliders, accessibility guidance requires adjustability, 90 h is 5 degrees from the Firewatch vertical default, and it returns about 1.36x more pixels per letter than 75 v at the same distance (12.8 vs 9.4 px at 1.5 m, 1080p). Caveat (adult eye height 1.6-1.7 m): shelf-top framing at the new eye height needs a Game-view check; if the top board gets cut off at the default, step the default to 95-100 h (63-68 v) before returning to 75 v. Implementation: `cm.Lens.FieldOfView = Camera.HorizontalToVerticalFieldOfView(h, 16f/9f)` on the Cinemachine camera, not on the `Camera` component (doc 02).
3. **Aspect: do not enforce 16:9 in code.** Hor+ already handles 16:10 (Steam Deck 1280x800, 101.7 h at 75 v, 84.0 h at 58.7 v [derived]), 4:3 and ultrawide. Keep `resizableWindow: 0` so odd windowed shapes cannot be produced by dragging; only `SetResolution` can produce them, so build the resolution list from `Screen.resolutions`, filter to unique width x height (drop refresh duplicates), and prefer 16:9 entries plus the native size. If a very wide screen needs capping later, reduce vertical FOV or use `Camera.rect` pillarboxing with a second black camera (pitfalls above). Also change the 1024x768 windowed default to 1280x720 on the next Player Settings pass (needs explicit approval under CLAUDE.md).
4. **UI scaling:** use Canvas Scaler Scale With Screen Size, 1920x1080 reference, Match = 1 (height). UNSOURCED GUESS; check at 16:10 and 21:9.
5. **Do not add head bob.** The project has none, which is already the safest default. If added, put it behind a 0-100% slider defaulting to 0 or off. Keep mouse smoothing off (it is on the GAG mismatch list) and offer separate X and Y sensitivity (XAG 117).
6. **Restate the earlier correction for the owner's brief:** wider FOV does not make things look closer or bigger; narrower FOV makes the shelf and books larger on screen at the same standing distance. Number: 17 percent of screen height for a 0.38 m book at 1.5 m with 75 v, 22 percent with 60 v, 22.5 percent with 58.7 v.
