# 24. Player (standalone) builds for performance testing, and an unattended perf smoke test

Research date 2026-10-18. Project: Unity 6000.6.6f1, URP 17.6, Windows x64 standalone, `com.unity.pipeline` 0.8.0-exp.1, Unity CLI 1.0.0-beta.13.
Method: web research (Unity manual/API, package docs, `Unity-Technologies/skills`, Microsoft Learn, Steam docs) plus read-only looks at local project files. Nothing was run in Unity, no build was made, nothing under `Assets/` or `ProjectSettings/` was edited.
Tags: **[fetched]** = I read the page; **[search-only]** = from a search summary, page not read; **[derived]** = my inference from fetched facts; **[local]** = read from this repo or the installed Editor; **UNSOURCED GUESS** = no source.
Builds on files 10 (batching), 19 (test framework / batch mode) and 20 (Editor focus).

## 1. Question

The Editor's numbers are not trustworthy, so the owner wants to confirm performance facts in a real Player. How do we make a fast Windows x64 Development Build without changing the committed `ProjectSettings/`; how do we run it unattended and capture frame time, draw calls, GC and screenshots; what do we measure and against what budgets; how does the Editor mislead; how are Frame Debugger / RenderDoc used on a Player; and what is the smallest repeatable "perf smoke test" the assistant can run from a shell (and what are its caveats about GPU use and window focus)?

## 2. Findings

### 2.1 Making a fast Windows x64 Development Build

- **Three supported ways to start a build.** (a) `BuildPipeline.BuildPlayer(BuildPlayerOptions)` from an Editor script, returns a `BuildReport`; `BuildPlayerOptions` has `scenes`, `locationPathName`, `target`, `targetGroup`, `subtarget`, `options`, `extraScriptingDefines`. [fetched] https://docs.unity3d.com/ScriptReference/BuildPipeline.BuildPlayer.html , https://docs.unity3d.com/ScriptReference/BuildPlayerOptions.html . (b) Editor command line `-buildWindows64Player path/to/build.exe` (with `-batchmode -quit`), or `-activeBuildProfile` + `-build`. [fetched] https://docs.unity3d.com/6000.0/Documentation/Manual/EditorCommandLineArguments.html . (c) The Unity CLI: `unity build --target StandaloneWindows64 --output-path X` (built-in desktop build), `--profile`, or `--execute-method Class.Method` (your method must honour `-buildOutput` and sets the exit code); `unity build run` launches the last recorded build; the page documents no dedicated development flag, so development options must come from your method or a Build Profile. [fetched] https://raw.githubusercontent.com/Unity-Technologies/skills/main/skills/unity-cli/references/build-run-test.md
- **Pipeline has an in-Editor `build` command.** `build` args: `target`, `outputPath`, `profileName`, `scenes` (defaults to Build Settings), `options` (case-insensitive `BuildOptions` names incl. `Development`, `AllowDebugging`, `ConnectWithProfiler`, `CleanBuildCache`, `DetailedBuildReport`), `confirm` (must be true), `dry_run`. It returns `queued` at once; **"an editor tick then runs the build, which is blocking"**; one build at a time; poll `build_status` (works during the build, reads a status file); the client must tolerate connection errors during a long build. `set_build_settings` changes `EditorUserBuildSettings` fields; `profileName` changes the active Build Profile. [fetched] https://docs.unity3d.com/Packages/com.unity.pipeline@0.8/manual/commands/build-and-compilation.html . The exact CLI spelling of these args is not shown; verify with `unity command --query build`.
  - Consequence [derived]: building inside the owner's open Editor freezes that Editor's UI for the whole build and needs the editor tick (see file 20 `set_autotick`). The alternative is a separate agent copy of the project built in batch mode (file 19 section 2.4), which costs one full import.
- **`BuildOptions` that matter.** `Development` (Profiler + assertions on), `ConnectWithProfiler`, `AllowDebugging` (needs Development), `CleanBuildCache`, `StrictMode` (fail on any error), `DetailedBuildReport`, `EnableDeepProfilingSupport`, `AutoRunPlayer`, `BuildScriptsOnly`. [fetched] https://docs.unity3d.com/ScriptReference/BuildOptions.html
- **Scene list: the committed build list is wrong for the real game.** [local] `ProjectSettings/EditorBuildSettings.asset` contains only `Assets/Scenes/LibraryPrototype.unity`; `Lamplit.unity` is not in it. `BuildPlayerOptions.scenes` (or Pipeline `build --scenes`) overrides the list per call; "If empty, only the currently open scene is built". [fetched] BuildPipeline.BuildPlayer page above. So no ProjectSettings change is needed: pass the scene list explicitly. (Build Profiles can also carry their own scene list, stored as an asset under `Assets/Settings/Build Profiles`, not in ProjectSettings. [fetched] https://docs.unity3d.com/Manual/build-profiles-reference.html , https://docs.unity3d.com/ScriptReference/Build.Profile.BuildProfile.html. Whether activating a profile rewrites something in `ProjectSettings/` is not documented; Pipeline's docs say `profileName` "changes the active profile".)
- **Overriding Player Settings per build without touching global settings.**
  - Build Profile "Customize player settings" overrides start from the global values and store only the overrides; "you can change a profile without modifying the global Project Settings"; overrides apply in Play mode and the Player; while a profile is active, Player Settings API writes update the override. Where overrides are stored is not documented. [fetched] https://docs.unity3d.com/6000.1/Documentation/Manual/build-profiles-override-settings.html , https://docs.unity3d.com/Manual/build-profiles-reference.html
  - **Runtime overrides need no setting at all:** `Application.runInBackground = true` (default false: "the application pauses when it is in the background"), `QualitySettings.vSyncCount = 0` (with `targetFrameRate = -1` the player runs uncapped; `vSyncCount > 0` makes `targetFrameRate` be ignored), resolution via command line, quality level via `-screen-quality`, graphics API via `-force-d3d11`. [fetched] https://docs.unity3d.com/ScriptReference/Application-runInBackground.html , https://docs.unity3d.com/ScriptReference/QualitySettings-vSyncCount.html , https://docs.unity3d.com/ScriptReference/Application-targetFrameRate.html , Player args page in 2.2.
  - **Scripting defines per build:** `BuildPlayerOptions.extraScriptingDefines` are "added to the Scripting Define Symbols already set in Player Settings". [fetched] https://docs.unity3d.com/ScriptReference/BuildPlayerOptions.html . A `[RuntimeInitializeOnLoadMethod]` static method in a plain class runs without any scene object, in the Editor and the Player. [fetched] https://docs.unity3d.com/ScriptReference/RuntimeInitializeOnLoadMethodAttribute.html . `Debug.isDebugBuild` is true only for Development Builds (and always in the Editor). [fetched] https://docs.unity3d.com/ScriptReference/Debug-isDebugBuild.html . Together these let a perf harness live in `Assets/_Project/` and switch on only in a Development Player given a command-line flag, with zero ProjectSettings edits. [derived]
  - Current committed values that matter [local, `ProjectSettings/ProjectSettings.asset`, `QualitySettings.asset`]: `runInBackground: 0`; `fullscreenMode: 1` (Fullscreen Window); default window 1024x768; Windows graphics APIs list `m_Automatic: 0` with `0x02` then `0x12` = Direct3D11 then Direct3D12 (my decoding of the `GraphicsDeviceType` enum, [derived]); `scriptingBackend` has only an Android entry (Windows standalone uses the default); `vSyncCount: 0` in both quality levels; the PC quality level uses `PC_RPAsset` (4 cascades to 50 m, 2048 main and additional shadow atlases, soft shadow quality 3, SRP Batcher on) and `PC_Renderer` with `m_RenderingMode: 2` (Forward+ in the URP enum, [derived]).
- **Mono vs IL2CPP.** Unity: IL2CPP build times "can be significantly longer than when using Mono" (AOT); exclude project and build folders from anti-malware scans and keep them on an SSD; IL2CPP Code Generation "Faster (smaller) builds" cuts build time at some runtime cost. [fetched] https://docs.unity.cn/Manual/scripting-backends-il2cpp.html (the docs.unity3d.com copy of this page had no such text, so the content is from the .cn mirror of the 6000.0 manual). Mono is the JIT backend; IL2CPP is "required on several platforms where Mono and JIT are not supported", which does not include Windows desktop. [fetched] https://docs.unity3d.com/Manual/scripting-backends.html
  - **Local fact:** the installed Editor 6000.6.6f1 has only `win64_player_development_mono` / `win64_player_nondevelopment_mono` (and 32-bit, arm64 mono) variations under `PlaybackEngines/windowsstandalonesupport/Variations`; there is no `*_il2cpp` variation, so the IL2CPP Windows module is not installed. [local] Mono is therefore both the fast and the only option today.
  - Caveat [derived]: Mono JIT vs IL2CPP code differ in script CPU speed, so absolute script timings from a Mono Player are not final-ship numbers. For this game (rendering- and physics-bound, little script work) that matters little; re-measure once in IL2CPP before shipping. How much slower Mono is: **UNSOURCED GUESS**; no source quantified it.
- **Incremental builds.** Standalone Windows uses the incremental build pipeline by default (only changed parts rebuilt; works with Mono and IL2CPP); "Clean Build" is for when callbacks (`IPreprocessShaders` etc.) changed. [fetched] https://docs.unity.cn/Manual/incremental-build-pipeline.html . So reuse the same output folder between builds.
- **Build time expectation.** No source gives minutes for Windows Mono builds. Read `BuildReport.summary.totalTime` (and `result`, `totalErrors`, `totalSize`, `outputPath`) from every build and keep the number. [fetched] https://docs.unity3d.com/ScriptReference/Build.Reporting.BuildSummary.html . My expectation for a small URP project: first build several minutes (shader variant compile dominates), later incremental builds well under that: **UNSOURCED GUESS**.
- **What the build needs.** Windows build support (installed, [local]); a scene list; an output path; the Editor not mid-compile. Unsaved scene edits are not in the build (the build reads saved assets) [derived, consistent with CLAUDE.md rule 5: save before anything that could modal]. `BuildPlayer` "invalidates editor script variables that reference GameObjects". [fetched] BuildPlayer page.

### 2.2 Running a Player unattended and capturing data

**Player command-line arguments** [fetched] https://docs.unity3d.com/Manual/PlayerCommandLineArguments.html:
- `-batchmode`: "Run the application in headless mode." `-nographics`: "skips graphics device setup" and turns log output off ("Log output is turned off in this mode" per that page). The desktop headless page defines headless as `-batchmode -nographics` and says it is for CI without a GPU. [fetched] https://docs.unity3d.com/6000.6/Documentation/Manual/desktop-headless-mode.html . Note the Player-args page says `-batchmode` alone is "headless mode" while the headless page defines it as `-batchmode -nographics`: the docs are not precise about what `-batchmode` alone does to rendering.
- `-screen-width`, `-screen-height` (must be supported resolutions), `-screen-fullscreen 0|1`, `-window-mode exclusive|borderless`, `-popupwindow` (frameless), `-monitor N` (1-based), `-screen-quality <name>`, `-single-instance`.
- `-force-d3d11`, `-force-d3d12`, `-force-vulkan`, `-force-device-index`, `-force-gfx-direct` (single-threaded rendering).
- `-logFile <path>` ("-" = console on Windows), `-nolog`, `-timestamps`, `-log-memory-performance-stats` (memory report at exit).
- Default Player log on Windows: `%USERPROFILE%\AppData\LocalLow\<Company>\<Product>\Player.log`. [fetched] https://docs.unity3d.com/Manual/log-files.html . The page does not say whether it is overwritten per launch; always pass `-logFile`.
- **Your own arguments:** the Player does not reject unknown args. Read them with `System.Environment.GetCommandLineArgs()` [derived, standard .NET; no Unity page fetched].
- **Exit:** `Application.Quit(int exitCode)` returns the code on Windows, Mac, Linux; "ignored in the Editor". [fetched] https://docs.unity3d.com/ScriptReference/Application.Quit.html . A shell can therefore read `$?` / `$LASTEXITCODE`.

**Rendering without a visible window?** Official docs: headless = `-batchmode -nographics` = no graphics device. Without `-nographics`, community posts say batch mode keeps a graphics device and `ScreenCapture`/RenderTexture capture can work, but others report black images and say you need a GPU and a desktop session; none are staff. [search-only + fetched thread] https://discussions.unity.com/t/capture-screenshots-in-batchmode/754535 . **Unknown, needs one experiment**: run once with `-batchmode` (no `-nographics`) and check Player.log's graphics line and whether screenshots are non-black. Do not plan on it.

**Profiler on a Player.**
- Development Build; optionally **Autoconnect Profiler** ("Editor embeds its IP address in the build, and the player connects to that address at startup") and Deep Profiling Support ("adds a small amount of overhead to your build"). Connection is by local network, cable or IP; "Continuously collect data" needs Run In Background enabled. [fetched] https://docs.unity.com/en-us/engine/6000.6/manual/analysis/profiler/profiling-applications/profiling-target-device.md , https://docs.unity3d.com/Manual/profiler-build-settings-reference.html
- **Headless capture to a file: `-profiler-enable`** (for a player = Autoconnect), **`-profiler-log-file <path>.raw`** (stream to a .raw file at startup, players and Editor), **`-profiler-capture-frame-count <N>`** (players only), **`-profiler-maxusedmemory <bytes>`** (default 16 MB for players, 256 MB for the Editor), `-connection-id`. The page does not say whether a Development Build is required or what happens if the frame count is omitted. [fetched] https://docs.unity.cn/6000.6/Documentation/Manual/profiler-command-line-arguments.html
- Saved captures: Profiler save writes `.data` into the project's `ProfilerCaptures`; `.raw` comes from `-profiler-log-file`; Import accepts either. [search-only] https://docs.unity.com/en-us/engine/6000.5/manual/analysis/profiler/window . Opening them needs the Profiler window in the Editor, so this is for a human look, not for the shell loop.
- Script API: `Profiler.logFile` + `Profiler.enabled` + `Profiler.enableBinaryLog`; "most of the Profiler API functionality is only available when you enable the Development Build option". [fetched] https://docs.unity3d.com/ScriptReference/Profiling.Profiler.html
- **Profile Analyzer** compares two captures (median frame etc.) and notes keeping the `.raw`/`.data` beside the `.pdata`; it has no pass/fail threshold. [search-only + fetched] https://docs.unity3d.com/Packages/com.unity.performance.profile-analyzer@1.2/manual/index.html , https://docs.unity3d.com/Packages/com.unity.performance.profile-analyzer@1.4/manual/workflows.html

**In-process counters (best fit for a CSV).**
- **`ProfilerRecorder`** works in Editor and Player "including Release Players"; `StartNew(category, name)`, `LastValue` = value at frame end; must `Dispose`; `ProfilerRecorderHandle.GetAvailable` lists usable metrics. [fetched] https://docs.unity3d.com/ScriptReference/Unity.Profiling.ProfilerRecorder.html
- Rendering counters, with a "Release Player" column: SetPass Calls, Draw Calls, Batches, Triangles, Vertices, Render Textures, Used Buffers, Vertex/Index Buffer Upload, **Shadow Casters Count** are available in release players; Static Batching / Instancing breakdown counters and Used Textures are not. Recorder names in the page's own example: `ProfilerCategory.Render`, "SetPass Calls Count", "Draw Calls Count", "Vertices Count". [fetched] http://docs.unity3d.com/Manual/ProfilerRendering.html (batch/triangle recorder names: take them from `GetAvailable`, I did not see them spelled out)
- Memory module chart counters: Total Used Memory, GC Used Memory, **GC Allocated In Frame**; the Objects-stats "GC allocated in frame" row "aren't available in release players". Whether the recorder `ProfilerCategory.Memory, "GC Allocated In Frame"` works in a Development Player: probable but not confirmed on a page; confirm via `GetAvailable`. [fetched] https://docs.unity3d.com/Manual/ProfilerMemory.html ; the recorder name is a [search-only] inference.
- **`FrameTimingManager`**: CPU and GPU frame timings with lower overhead than the Profiler; `CaptureFrameTimings()` then `GetLatestTimings(n, array)`; results lag **four frames**; GPU time can be 0 if the GPU returns no result; always active in Development Players, in release builds needs Player Settings "Frame Timing Stats" (a ProjectSettings change) or an attached `ProfilerRecorder`. `FrameTiming` fields in ms: `cpuFrameTime`, `cpuMainThreadFrameTime`, `cpuMainThreadPresentWaitTime`, `cpuRenderThreadFrameTime`, `gpuFrameTime`. [fetched] https://docs.unity3d.com/ScriptReference/FrameTimingManager.html , https://docs.unity3d.com/ScriptReference/FrameTiming.html
- Memory snapshot from a Player: `MemoryProfiler.TakeSnapshot(path, callback, flags)` works with no Editor connected (file is created on the Player host; relative paths resolve against `Application.dataPath`); recommended coroutine; rename `.tmpsnap` to `.snap`. [fetched] https://docs.unity3d.com/ScriptReference/Unity.Profiling.Memory.MemoryProfiler.TakeSnapshot.html . Run once per room for a leak check, not per frame.

### 2.3 What to measure for this game, and budgets

- **Frame budget arithmetic:** 60 fps = 16.66 ms; 30 fps = 33.33 ms; "Even a single frame that exceeds the target frame budget will cause hitches"; "Don't worry about fps unless you drop below your target"; a project is bound by "the chip and/or thread that takes the longest". [fetched] https://unity.com/how-to/best-practices-for-profiling-game-performance
- **CPU vs GPU bound reading:** main thread `Gfx.WaitForPresentOnGfxThread` + render thread `Gfx.PresentFrame` = GPU-bound; main thread waiting on render thread = render-thread bound; `WaitForTargetFPS` = idle headroom (same page). With `FrameTiming`: compare `cpuMainThreadFrameTime`, `cpuRenderThreadFrameTime`, `gpuFrameTime` to `cpuFrameTime` [derived].
- **Target hardware (Steam).** Steam Hardware Survey, September 2026: primary display 1920x1080 47.91%, 2560x1440 27.04%, 3840x2160 4.79%; top GPUs RTX 5070 (5.86%), RTX 5060, RTX 5060 Ti, RTX 4060, RTX 3060 (3.54%). [fetched] https://store.steampowered.com/hwsurvey/ . **Sources disagree on 1440p**: older articles give 1080p at 61-65% and 1440p at 4-11% [search-only: PCGamesN, TechSpot, Mein-MMO via search]; the Valve page is the primary source and the most recent. Steam Deck Verified: default settings must give a playable framerate; the page sets the target at 30 fps at 800p for Deck and 30 fps at 1080p for Steam Machine; native 1280x800 preferred; smallest font 9 px at 1280x800 (12 px recommended). [fetched] https://partner.steamgames.com/doc/steamdeck/compat
- **Proposed budgets** [derived from the above; the numbers are my choices, not Unity's]: 1080p and 1440p on the dev GPU: p95 frame <= 8.3 ms (leaves headroom to hit 60 fps on a GPU roughly 2x slower), p99 <= 16.6 ms, no frame > 33 ms in a scripted walk; Deck-class check (1280x800 or render scale ~0.6) p95 <= 33 ms. The "2x slower GPU" factor and the 8.3 ms figure are **UNSOURCED GUESS**.
- **Draw calls / SetPass:** no Unity number for PC. The only figures are one practitioner's "aim for under ~2000 draw calls on low/medium PCs" (low confidence, file 10). The measured number matters less than whether CPU main and render thread times fit the frame. Record Batches, Draw Calls, SetPass Calls per room. (counter definitions above; ProfilerRecorder example [fetched])
- **GC allocation per frame:** Unity gives no "zero" number; the guide only says to find and remove unwanted managed allocations in the core loop and that allocation cost is understated in the Profiler. Incremental GC is on by default, "Non-incremental mode stops the main thread for one long pause, which can last hundreds of milliseconds"; Unity suggests calling `System.GC.Collect` after releasing a level's long-lived memory and before loading the next. [fetched] https://unity.com/how-to/best-practices-for-profiling-game-performance , https://docs.unity3d.com/Manual/performance-incremental-garbage-collection.html . `[local]` project has `gcIncremental: 1`. Rule for the harness: steady-state walking should allocate 0 B per frame; flag any frame with > 1 KB (the 1 KB threshold is **UNSOURCED GUESS**).
- **Shadow cost:** URP shadow counters: "Shadow Casters Count" (release-available). To get the GPU-time cost of shadows, run the same path twice and change one thing per run. `UniversalRenderPipelineAsset` has runtime setters for `shadowDistance`, `shadowCascadeCount`, `mainLightShadowmapResolution`, `additionalLightsShadowmapResolution`, `renderScale`, `msaaSampleCount`, `maxAdditionalLightsCount`; `supportsSoftShadows`, `supportsMainLightShadows`, `supportsAdditionalLightShadows` are getters only. [fetched] https://docs.unity3d.com/Packages/com.unity.render-pipelines.universal@17.0/api/UnityEngine.Rendering.Universal.UniversalRenderPipelineAsset.html (17.0 page; this project has URP 17.6). **Danger** [UNSOURCED GUESS]: writing these properties in the Editor's Play mode may dirty/persist to the asset; only do it in a Player (the Player has its own in-memory copy), driven by a command-line flag like `-perf-shadows off`.
- **Load time of a room:** no source for numbers. Measure with `System.Diagnostics.Stopwatch` from the call that activates a room (file 12: `SetActive`) until two rendered frames later, and record the worst frame in that window; shader first-use stalls are the real risk: Unity "might" stall the first time a variant renders because the driver builds a GPU-specific version, then caches it. [fetched] https://docs.unity3d.com/Manual/shader-loading.html . A scripted walk that enters each room for the first time shows this; the Editor hides it differently (see 2.4).
- **Memory:** `Total Used Memory`, `GC Used Memory`, `System Used Memory` by recorder (example in the ProfilerRecorder page [fetched]); one `TakeSnapshot` per room optional. No PC memory budget from sources; the game is tiny so just record and watch for growth between rooms/revisits [derived].
- **Mean is not enough:** report p50, p95, p99, max and the count of frames over 16.6 and 33.3 ms. Median is the natural baseline statistic (Profile Analyzer workflow, [search-only]).

### 2.4 Editor vs Player: why Editor numbers mislead

- Unity: "the most accurate profiling results always come from running and profiling builds on target devices"; Editor profiling is for major issues. [fetched] https://unity.com/how-to/best-practices-for-profiling-game-performance
- Play mode has Editor-only work, shown as **EditorLoop** markers; other open Editor windows consume render-thread and GPU time; the Game view should be maximised so resolution is realistic for fill-rate. [fetched] https://docs.unity3d.com/Manual/profiling-play-mode.html
- The Stats overlay's **main thread time includes "the time Unity takes in the Editor to update the Scene view"** and other Editor windows; render-thread time "doesn't include the time Unity takes in the Editor"; Estimated Graphics Memory is an estimate; Stats are an overlay of Play mode only. [fetched] https://docs.unity3d.com/Manual/RenderingStatistics.html , file 10.
- Game view specifics: "Low Resolution Aspect Ratios" always on for non-Retina displays (renders fewer pixels than the window), a Scale slider, Gizmos menu, a Game-view-only VSync toggle ("attempts" the monitor refresh rate). [fetched] https://docs.unity3d.com/Manual/GameView.html . So Game-view pixel count, gizmos and vsync are not the same as a 1080p Player.
- `Debug.isDebugBuild` is always true in the Editor, so any "debug-only" code path (extra logging, asserts) runs in the Editor and in Development Players but not in a release Player. [fetched] https://docs.unity3d.com/ScriptReference/Debug-isDebugBuild.html
- Run-in-background is treated as always on in the Editor, but a Player pauses when unfocused unless `runInBackground` is set (file 20; [fetched] https://docs.unity3d.com/ScriptReference/Application-runInBackground.html). This is why an unattended Player needs `Application.runInBackground = true` set in code.
- Shader variants: in a build Unity loads only compiled/stripped variants and the driver compiles each on first use ("visible stall"); a stripped-but-needed variant falls back to the magenta error shader. [fetched] https://docs.unity3d.com/Manual/shader-loading.html . The Editor's asynchronous shader compilation page returned 404, so the Editor's behaviour is **UNSOURCED**: do not assume first-use hitches are visible in the Editor.
- Scripting runtime: Editor uses Mono JIT; a Player on Mono is the same family; IL2CPP differs (see 2.1). Development Player vs release Player: Development adds the Profiler, assertions and (if enabled) deep-profiling support overhead; overhead size **UNSOURCED GUESS**. For a "true" number, a release build still exposes `ProfilerRecorder` counters and `FrameTimingManager` (via an attached recorder) [fetched above], so the harness can run in a non-development build too, just without Profiler/Frame Debugger/Pipeline runtime.
- Forum anecdotes both directions (a game at 60 fps in the Editor and 35-45 fps as a build; cause in one thread was graphics API/GPU selection or quality tier). Use only as a warning that a Player can be slower, not as evidence. [search-only] https://discussions.unity.com/t/game-runs-faster-in-editor-than-in-build/883020 and related threads.

### 2.5 Frame Debugger and RenderDoc on a Player

- **Frame Debugger** can attach to a built Player: the target selector "specifies the process to attach the Frame Debugger to". Requirements: **Development Build**, multithreaded rendering (all platforms except Web), and on desktop **Run In Background** (otherwise clicking the Frame Debugger window makes the player lose focus and it stops reflecting rendering changes); the running app is paused while a frame is captured. [fetched] https://docs.unity3d.com/6000.2/Documentation/Manual/FrameDebugger-attach.html , https://docs.unity3d.com/Manual/frame-debugger-window.html . It lives in the owner's Editor window, so it is a human tool, not part of the unattended loop. Use it to answer "why is this draw not SRP-batched" (Batch cause row, file 10) in a real Player.
- **RenderDoc** works on standalone players "with no extra setup"; only if Unity runs on a platform and API RenderDoc supports (D3D11/D3D12 on Windows qualify, [derived]); the Unity integration button and `-load-renderdoc` are Editor-only; D3D11 shaders strip debug info by default, add `#pragma enable_d3d11_debug_symbols` to keep names/source. [fetched] https://docs.unity3d.com/6000.2/Documentation/Manual/RenderDocIntegration.html . Launch the exe from RenderDoc with `-force-d3d11 -screen-width ... -logFile ...`; a command-line `renderdoccmd` capture path exists but I did not research it (**UNSOURCED**). Capture is GUI work for the owner or a scheduled session; not part of the smoke test.
- Both tools need Development Build + a window on the real GPU; neither gives unattended numbers. They answer "why" after the smoke test says "which room/which metric regressed".

### 2.6 Focus and the window problem

- A process may take the foreground only if, among other things, it was started by the foreground process, or it received the last input, or the foreground lock timeout has expired; otherwise "Windows flashes the taskbar button" instead. [fetched] https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow . Which case applies to a Player launched by the assistant's shell, is unknown [derived: if the shell is a child of the terminal/app the owner is looking at, it may be allowed to take focus].
- The first `ShowWindow` call's `nCmdShow` is ignored if the launcher provided a `STARTUPINFO` show state; `SW_SHOWMINNOACTIVE` / `SW_SHOWNOACTIVATE` show a window without activating it. [fetched] https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow . Whether Unity honours the launcher's show state, and whether a minimised Unity window keeps rendering normally, is **UNSOURCED**. PowerShell's `Start-Process -WindowStyle Minimized/Hidden` sets such a state [UNSOURCED GUESS on exact mapping]; a minimised window may also render at a different cost. Do not use a minimised window for GPU numbers without checking.
- Safer: `-monitor 2` (fetched arg) on a second monitor, `-popupwindow` (frameless), or run when the owner is away. A running fullscreen/borderless Player over the owner's work is disruptive in any case.

## 5. Implication for BookBoy

**Recommendation: write a small self-driving perf harness in a Development Player; do not add packages and do not touch ProjectSettings.** It stays inside `Assets/_Project/` (not `Starter Assets`), small and single-purpose, in line with CLAUDE.md.

**Build (no ProjectSettings change).**
1. An Editor method `PerfBuild.Build` (in `Assets/_Project/Editor/`) calling `BuildPipeline.BuildPlayer` with `scenes = { Assets/Scenes/Lamplit.unity }`, target `StandaloneWindows64`, `options = Development | StrictMode | DetailedBuildReport`, output `<outside Assets>/Builds/perf/BookBoy.exe`; log `summary.result`, `totalTime`, `totalSize`, `totalErrors`. Mono is the only backend installed anyway. Reuse the output folder (incremental).
2. Start it via Pipeline's `build` command (`confirm true`, `scenes`, `options Development`) and poll `build_status`, or by `-executeMethod PerfBuild.Build` in a separate agent copy (file 19). Warn the owner that the first option blocks their Editor for the build duration, and run `set_autotick` first (file 20). Prefer the agent copy if a build takes more than a minute or two once measured.
3. After the very first build check that no tracked file under `ProjectSettings/` changed (if one did, stop and tell the owner).

**Harness (`Assets/_Project/Scripts/Perf/PerfSmoke.cs`, runtime).** A `[RuntimeInitializeOnLoadMethod]` that does nothing unless `Debug.isDebugBuild` and the command line contains `-perf`. When active: set `Application.runInBackground = true`, `QualitySettings.vSyncCount = 0`, `Application.targetFrameRate = -1`; start `ProfilerRecorder`s (SetPass, Draw Calls, Batches, Triangles, Shadow Casters, GC Allocated In Frame, Total Used Memory; dump `ProfilerRecorderHandle.GetAvailable` names once to the log) and use `FrameTimingManager`; follow a scripted camera path hub -> room 1 -> 2 -> 3 -> back by teleporting between waypoints and calling the game's own room-activation entry points (no input devices, so no focus rules, file 20); per room: 120 warmup frames, 600 measured frames, one `ScreenCapture.CaptureScreenshot` (absolute path, wait 2 frames); time each room's first activation with a Stopwatch; write `frames.csv` (one row per frame: frame, room, cpu/main/render/gpu ms, draw calls, SetPass, batches, tris, shadow casters, GC bytes, memory) and `summary.json` (p50/p95/p99/max, counts over 16.6 and 33.3 ms, per room); `Application.Quit(0)` on success, non-zero on exception or timeout (a watchdog quits after N seconds). Optional flags: `-perf-shadows off|lowres`, `-perf-scale 0.6` (for Deck-class), applied to the in-memory URP asset in the Player only.

**Run (shell, PowerShell).**
`Start-Process -Wait -PassThru <exe> -ArgumentList '-perf','-perf-out','<dir>','-screen-width','1920','-screen-height','1080','-screen-fullscreen','0','-popupwindow','-monitor','2','-force-d3d11','-screen-quality','PC','-logFile','<dir>\player.log','-timestamps'` then check `ExitCode`, `summary.json`, and grep the log for exceptions and for the graphics device line. Run twice (1080p and 1440p) and keep 3 repeats if the first looks noisy; take the median of medians. Optional deeper pass: add `-profiler-enable -profiler-log-file <dir>\run.raw -profiler-capture-frame-count 600` and open it later in the Profiler window.

**Compare.** A tiny script diffs `summary.json` against `Docs/perf/baseline.json` (committed, with GPU name, driver, resolution, Unity version and build time): fail on p95 or p99 worse by > 10% and > 0.5 ms, any frame > 33 ms, draw calls or SetPass up > 15%, or any steady-state GC allocation. Update the baseline only deliberately.

**Caveats to state to the owner.** It still uses the real GPU and shows a window (possibly taking focus; Windows may only flash the taskbar instead); results are noisy if the machine is busy; run when the owner is away or put the window on monitor 2; it measures one machine; Mono Development Player numbers are slightly pessimistic or optimistic relative to a shipped IL2CPP release build, so re-measure once in release/IL2CPP before launch. One-off experiment worth doing: try `-batchmode` without `-nographics` once to see if screenshots render without a visible window.

**Needs approval (not done):** the Pipeline runtime server (`RuntimePipelineConfig.json`), adding the Performance Testing package (`manifest.json`), turning on "Frame Timing Stats" or changing `runInBackground` in Player Settings, Build Profile creation if it rewrites tracked settings.

**What this changes in earlier research:** file 20 treated `capture_game_view` and `set_autotick` as the way to verify visually; this adds a second path that bypasses the Editor focus problem entirely (a Player is a separate process with `runInBackground` set in code), at the price of a real window and GPU use.
